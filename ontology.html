01 WHY A BASE LAYER

One use case is an integration. A hundred is a liability.

Every AI use case needs data from systems that already exist. The question is whether each one goes and fetches it, or whether they all draw from one governed layer.

Illustrative arithmetic based on the 13 source domains in section 2. The point is the shape of the curve, not the exact count at your institution.

What the layer carries that a direct call does not

  • One definition of a student. Written down once, owned by someone, inherited by every agent that reads it.
  • Permissions that travel with the data. Row and column level security applies underneath, not inside each application.
  • Lineage and governance. Where a number came from, who can see it, and what it means.
  • A place to add the next use case. The hundredth agent connects to one thing, not to thirteen.

03 WHAT THE ONTOLOGY ADDS

The same question, two correct answers.

A table gives you rows. An ontology gives you what the rows mean — and it names the difference instead of hiding it.

THE RELATIONSHIP THAT CARRIES THE MEANING

Event Registration links to Student only when attendee_type is Student, through a dedicated mapping table.

That is a definition somebody owns, written down once — and now every agent inherits it.

Why this is hard to do without an ontology

Nothing in the raw tables is wrong. The registration table faithfully records 1,200 registrations. The housing table faithfully records 148 assignments. The error appears the moment someone assumes a row means a person.

An ontology makes the institution state the rule once — which rows are people, which relationship means currently lives here versus holds a record here — so the agent never has to guess, and two teams asking the same question get the same answer.

05 GOVERNANCE

The boundary sits under the agent, not inside it.

Bringing the data together is only safe if the permissions come with it. This is the part that decides whether a second use case is a week or a quarter.

  1. 1
    Identity

    Who is asking. A student, an advisor, and a provost reach different rows of the same table.

  2. 2
    Row and column level security

    Applied in the platform, underneath every agent. An agent cannot read past it, because it never sees the rows.

  3. 3
    Governance and lineage

    Sensitivity labels and policies follow the data. Where a number came from is answerable.

  4. 4
    Read-only agents

    The agent generates a read query. It has no path to write.

THE HONEST LINE — SAY THIS ONE

I could show you the agent refusing to answer a question about another student. It will refuse. But that refusal comes from how the agent is scoped, and a prompt is not a security boundary. The real boundary is underneath, where identity decides which rows are reachable at all. I'm showing you the experience — I'm not going to demonstrate access control with a prompt.

The other half of trust: refusing to guess

When a question needs a relationship the institution has never recorded, the useful answer is to say so. An agent that names the missing link is telling you something true about how your institution records its own work.

SAY AFTER A REFUSAL

It did not guess. It told us exactly which relationship does not exist. That is a gap in how this institution records its own work — and now we know about it. This is the behaviour you want when the answer matters.
